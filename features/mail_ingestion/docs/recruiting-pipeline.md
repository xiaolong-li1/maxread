# ZIP Lab 招聘邮箱增量管线

## 1. 运行模型

`RECRUITING_SCAN_INTERVAL_DAYS` 控制扫描周期，`scan-once` 用于手动验收，`run` 用于常驻运行。每轮先执行只读 IMAP 增量扫描，再处理未消费的邮件线程。

```text
定时触发
  -> IMAP UID 增量扫描（Inbox + 自定义文件夹）
  -> MIME/线程归并
  -> PDF 本地文本提取
  -> AI 结构化抽取（新线程或有新候选人来信）
  -> 云文档创建/追加 + PDF 附件插入
  -> Feishu Base upsert
  -> run/message/thread 审计与失败重试
```

## 2. 新邮件、follow-up 与我方回复

线程键优先使用候选人地址 + 去掉 `Re/Fwd/回复` 前缀后的主题。Outlook 移动文件夹时可能丢失 `References`，所以不能只依赖 Message-ID 链。

- 新线程：调用一次 AI，创建候选记录和材料文档。
- follow-up：保留旧字段，输入旧结构化结果 + 新邮件/PDF，让 AI 只补充或更正有新证据的字段；更新时间取线程最新一封邮件。
- 我方回复：识别发件人等于邮箱账号的邮件，只追加原文到云文档、更新 `last_outgoing_time`，不创建新候选、不覆盖候选字段。
- 只有我方回复而没有历史候选来信：只记审计，不生成候选记录；之后收到对方回复时再建立线程。

## 3. 邮件类型与文件夹到人工状态

`邮件类型` 只保留两类：`候选人来信`（实习、套磁、推免、博士申请统一归入）和 `其他`（系统通知及完全无关邮件）。研究方向另由 `申请项目` 字段按背景映射到 MLSys、Agentic Infrastructure、Kernel Efficiency、World Model，不再用邮件类型承担方向区分。

模型阅读完整邮件往返后确认实验室明确拒绝（例如名额原因不再接收）时，且当前 `筛选状态` 仍为 `未筛选`，自动更新为 `未通过`。关键词只作为模型输入，不作为独立判据；候选人引用或转述旧拒信不会单独触发。已有人工状态以及 `面试资格` / `面试通过` 不被覆盖；规则只负责拒绝这一条单向终止分流。

模型不决定人工筛选结果。只有明确的邮箱文件夹映射会改变流程字段：

| 邮箱文件夹 | `筛选状态` | `是否已分配面试` |
|---|---|---|
| 面试寄 | 面试资格 | true（可由配置关闭） |
| 面试通过 | 面试通过 | true |

“初筛”不自动写状态；其他人工设置在 follow-up 时保持不变。

### 院校、排名与回复标签

每条 Base 记录额外维护 `院校`、`排名`、`排名依据`、`是否985`、
`是否C9`、`是否已回复`、`来源邮箱`。AI 读取完整线程和简历后分别提取
学业表现与排名，并复制最短的排名原文证据；代码不再用正则或数字启发式
推断排名，避免把 `94.73/100`、竞赛 `73/100` 或 GPA 当成名次。985 标签依据
[教育部公布的 39 所名单](https://www.moe.gov.cn/srcsite/A22/s7065/200612/t20061206_128833.html)，
C9 依据九校联盟成员口径；别名按完整院校分段匹配，避免把独立学院误标为
母体高校。`是否已回复` 直接来自线程是否存在我方 outgoing 邮件，不交给模型
猜测。标签采用“是/否/未知/不适用”，证据不足时不强行写否。

全量刷新使用：

```bash
./bin/recruiting-pipeline tag-records --dry-run
./bin/recruiting-pipeline tag-records --confirm
```

`--confirm` 会让每个非显然系统通知线程重新经过 AI，并在不修改人工筛选状态
的前提下更新 Base；云文档正文默认不重写。历史学业字段专项复核使用
`repair-academics --confirm`，同样调用 AI，不走本地数字规则。

### 多邮箱来源与去重

生产可通过 `RECRUITING_MAIL_ACCOUNT_ENVS` 配置多个只读账户。原始邮件以
`账户 + 文件夹 + UID` 存储，RFC `Message-ID` 作为跨账户内容去重键；因此
同一封邮件同时 CC 到 ZIP Lab 与 Bohan 时只进入线程一次，但 Base 的
`来源邮箱` 多选字段同时保留 `ZIP Lab`、`Bohan`。任一受管邮箱或组内成员
发出的线程回复都会令 `是否已回复=true`。来源为空属于数据错误，不允许写
`unknown`。同一时刻仍只运行一个 recruiting pipeline，由它顺序扫描所有
账户并串行写 Base。

没有直接接入 IMAP、但回复时会抄送受管邮箱的组员地址配置在
`RECRUITING_TEAM_ADDRESSES`（逗号分隔）。这些地址不作为邮件来源扫描，
只用于把回到 ZIP Lab/Bohan 的回复副本识别为 outgoing；若回复没有抄送任一
受管邮箱，管线无法观测。

## 4. 并发边界

- IMAP：单连接串行 select/fetch，避免共享连接状态和 UID 水位冲突。
- PDF：候选人之间可并发，默认 `RECRUITING_PDF_WORKERS=4`。
- AI：候选线程之间可并发，默认 `RECRUITING_LLM_CONCURRENCY=2`；同一线程串行，follow-up 必须看到上一版结果。
- 云文档、附件、Base：串行写入；同一线程不允许并发 append/upsert。

## 5. 模型路由

生产环境复用 Aliyun 私有配置中的 OpenAI-compatible API：

```dotenv
RECRUITING_MODEL=gpt-5.6-sol
RECRUITING_REASONING_EFFORT=medium
RECRUITING_OPENAI_BASE_URL=<private gateway>
RECRUITING_OPENAI_API_MODE=responses
```

普通新邮件和 follow-up 合并都使用 `gpt-5.6-sol` medium；模型只负责分类、字段抽取和短段落摘要，不负责人工筛选。候选摘要最多四行，按需分为申请目的、科研经历、论文/发表（含会议/状态）、奖项/竞赛。PDF 先本地 `pdftotext`，扫描件再扩展视觉输入，避免把整份 PDF 重复发给模型。

## 6. 重试与幂等

- 429、超时、连接错误、5xx：带抖动指数退避，默认最多 3 次，尊重 `Retry-After`。
- 400、权限、参数错误：不重试，写入失败记录等待人工处理。
- SQLite 保存 `thread_key`、`message_record_id`、`base_record_id`、`doc_id`、attempt/error；重启后继续未消费线程。
- 文档创建成功后先落库 token；附件按路径逐个追加。Base 使用已保存 record ID 更新，避免重复创建。
- 已有文档重跑时只追加新邮件片段，不重复写入完整结构化摘要；同名同分钟邮件若没有材料文档精确匹配，不会任意复用旧行，而是创建独立 Base 记录。

## 7. 运行与验收

```bash
./bin/recruiting-pipeline scan-once
./bin/recruiting-pipeline run --interval-days 1
./bin/recruiting-pipeline status
```

生产部署位于 Aliyun `/opt/maxread/features/mail_ingestion`，使用系统级
`recruiting-pipeline.service`。第一轮建议 `scan-once`，检查新增线程、
follow-up 合并、面试寄映射、云文档链接和失败重试统计，再启用常驻服务。

## 8. 已发生问题与永久防护

| 问题 | 根因 | 现在的防护 |
|---|---|---|
| PDF 已下载但成绩/排名为空 | 5090 没有 `pdftotext`，旧逻辑静默返回空文本 | `pdftotext` 不可用时使用 PyMuPDF/fitz；PDF 文本先本地抽取，再送给模型；抽取失败保留明确空文本标记 |
| Base 出现同名重复候选 | 远端 CLI 不接受旧的 `--limit 2000`，查询失败后当作“没有记录”继续创建 | 记录查询固定使用服务端上限 200；优先复用已有 `record_id` 或材料文档链接；同名同分钟有多个候选时不任意覆盖 |
| 组内成员个人邮箱回复变成新候选 | 线程键只使用发件人地址 + 主题，没有解析 `In-Reply-To/References` | 按 Message-ID 引用归并；候选人是 incoming，其他组内参与者是 outgoing；加载和同步使用同一归并算法 |
| 同一份简历在云文档出现多次 | 文档更新接口可能异步重放 token 化媒体资源，重试也可能重复插入 | 本地按 SHA-256 登记已上传附件；更新结束等待媒体落稳后按文件名清理重复 file-card；每轮验收附件计数 |
| 重跑后摘要/邮件正文重复 | 旧逻辑对已有文档追加完整线程 | 已有文档只追加未处理的新邮件；结构化字段局部刷新，不再追加整份摘要 |
| 候选邮件被错误区分为实习/套磁，或项目显示 unknown | 邮件类型和研究方向被混在一起，模型只看显式项目词 | 邮件类型统一为候选人来信；申请项目根据 PDF/邮件背景映射到四个 topic，3D、RL、System Efficiency 等别名也归到最近方向 |
| 邮件正文里的 163 超大附件漏掉 | 附件不是 MIME 实体，而是短期外链 | 允许的 163 外链先解析、下载、校验 `%PDF`，落盘后再进入抽取和飞书上传；过期/无权限链接必须记录失败，不伪装成已上传 |

每次变更后必须做三项验收：`run.failed_threads = 0`、本地附件与文档 file-card 数量一致、候选项目无 `unknown`。任何一项不满足时，任务保留失败状态并等待重试，不将半成品标记为完成。

## 10. 招聘周报

周报只发送候选池的摘要，不把邮件正文或 PDF 直接铺到群里：

- 统计过去 7 天有新邮件或线程更新的候选人数量；
- 只汇总候选池、未筛选和最近一周新增数量，不把候选人明细重复刷到群里；
- 提供“候选人池”“未筛选池”“最近一周新增”和四个方向视图入口；未筛选池同时过滤 `邮件类型=候选人来信` 和 `筛选状态=未筛选`，多 topic 候选人会在多个方向视图出现，但底层 record、状态和材料文档只有一份。

`weekly-report --send --chat-id <oc_xxx>` 用于发送一次周报；发送使用按周生成的幂等键，重复执行不会重复发同一周消息。部署 `deploy/recruiting-weekly-report.service` 和 `.timer` 后，默认每周一 07:00（Asia/Shanghai）发送；群 ID 通过 `RECRUITING_NOTIFY_CHAT_ID` 配置，未配置时不启用 timer。

## 9. 事件矩阵与状态优先级

| 事件 | 处理方式 | 是否调用 AI | Base 状态 |
|---|---|---|---|
| 新候选人首信 | 建立线程、落盘全部附件、创建材料文档、写入候选人来信 | 是 | 默认未筛选 |
| 候选人 follow-up | 按 Message-ID/引用归并；AI 读取完整线程和新增附件；文档仅追加新增片段 | 是 | 保留人工状态 |
| 公共邮箱回复 | 归并到原线程；不新建候选人；记录回复并让模型判断是否明确拒绝 | 是 | 仅允许未筛选 → 未通过 |
| CC 同学个人邮箱回复 | 按引用或转发头中的原始候选地址归并；视为我方回复 | 是 | 同上 |
| 邮件移动到“面试寄” | 只作为人工明确推进信号 | 否 | 未筛选 → 面试资格 |
| 邮件移动到“面试通过” | 只作为人工明确推进信号 | 否 | 面试资格 → 面试通过 |
| 明确拒绝 | 模型输出 `rejection_recommendation=未通过` | 是 | 仅未筛选 → 未通过 |
| 其他系统通知 | 不调用模型，保留一条描述和原文档 | 否 | 不进入候选流程 |

状态合并遵循：Base 当前值 > 本地缓存；终态 `未通过 / 面试通过 / 实习生` 不会被低级信号倒退；`是否已分配面试` 只增不减；`面试结果` 一旦人工填写，不被邮件扫描覆盖。服务每轮先读取 Base 当前状态，再提交候选字段更新。
